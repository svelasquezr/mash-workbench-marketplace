# review-routing

A Claude Code plugin that sends each change to the reviewers it needs. A project lists its specialist reviewer agents and the paths each one covers in `.claude/reviewers.toml`; a general `change-reviewer` covers every path no specialist claims. Reviewers are read-only and end with a verdict line (`SAFE TO LAND` or not), which the `review-changes` summary checks.

## Install

```
/plugin marketplace add svelasquezr/mash-workbench-marketplace
/plugin install review-routing@mash-workbench-marketplace
```

To try it without installing: `claude --plugin-dir <path-to>/plugins/review-routing`.

## What it contains

| Part                                        | What it does                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `review-changes` skill                      | before you open a pull request: picks the reviewers and their models for your committed changes, runs your checks first, dispatches the reviewers, triages findings and fixes what the change introduced; prints a summary in the terminal and writes nothing to a PR                                                  |
| `add-reviewer` skill                        | adds a specialist reviewer when the bugs a review passed in one area reach the escape threshold (default 3), and records each one as a file in `.claude/mash-workbench/escapes/`                                                                                                                                       |
| `record-escape` skill                       | when you process review comments, paste one, or correct code a review passed: checks that a review passed the code (the review log, or your answer) and that the problem is a behavior bug, then records it as an escape file and asks about a specialist reviewer at the threshold; never commits, pushes or comments |
| `inspect` skill (`/review-routing:inspect`) | for a project that already has review habits: finds instructions in `CLAUDE.md`, `AGENTS.md`, memory or plans that would override the routing, and areas you already brief reviewers on by hand; proposes rewrites and applies only the ones you approve                                                               |
| `change-reviewer` agent                     | the default, read-only reviewer: correctness, tests for new branches, stale docs, unsupported claims, secrets                                                                                                                                                                                                          |
| `reviewer-guard` hook                       | refuses the plugin's reviewers (its own agents and the ones your `.claude/reviewers.toml` names) their non-read git commands (in a real repository, not a scratch one) and their GitHub-writing `gh` commands (a guard against accidents, not a security boundary; the gaps are listed in the hook's docstring)        |

## Requirements

`git`, `bash` and Python 3.11 or newer, found as `python3`, `python` or the Windows launcher `py -3` (the Microsoft Store alias does not count; set `MASH_PYTHON` to choose one: a command such as `py -3.12`, or a full path to the interpreter, which may hold spaces but then takes no arguments). With none, the review runs only the general reviewer and says routing was skipped. Nothing needs `gh` or GitHub: the review works on a git range, whatever hosts the repository. Recording an escape needs only `bash` (no `python3`), and the skills say how to write the file by hand if the script cannot run. Source links from github.com are normalised; any other http(s) link is kept as given. Built for Claude Code and developed against 2.1.289; older versions are untested. `inspect` reads the project's `CLAUDE.md` and `AGENTS.md` and, where they exist, `.claude/memory/`, `.claude/plans/` and the auto-memory folder under `~/.claude/projects/`.

## Opinionated defaults

- The routing config rejects Haiku, the router never prints it, and `review-changes` tells the session to use the models the router prints. Nothing checks a direct dispatch or a fix-round dispatch any more.
- Models in `.claude/reviewers.toml` are the aliases `sonnet`, `opus` and `fable`, the ones Claude Code's agent tool accepted when this plugin was written. If your Claude Code accepts other aliases, the config check rejects them until the list in `route_types.py` is updated. Pin only models your plan can start: a reviewer pinned to a model you cannot use fails when it is dispatched.

## Verdict format

Every reviewer this plugin runs, including the ones `add-reviewer` writes from its template, ends its review with exactly one line: `SAFE TO LAND` when it found no Critical and no Important problems, or `NOT SAFE: <why>` otherwise. Minor findings never block. `review-changes` calls the branch ready to open as a PR only when every reviewer's last verdict is `SAFE TO LAND`. A reviewer you write by hand should end the same way, or `review-changes` cannot read its verdict. Reviewer files copied from an older version of the template may still say "ready for `gh issue create`" under Pre-existing; they keep working, and the new wording is "ready to file as an issue".

## What the hook does to your session

The hook applies in every project once the plugin is enabled, not only in projects that use review routing. It runs on every Bash call (around 15 ms each; for a reviewer's git command that is not a plain read, `reviewer-guard` also runs `git rev-parse` once per directory and git dir the command touches) and writes nothing.

- `reviewer-guard` acts only for this plugin's reviewers: its own `review-routing:` agents, and the agents your `.claude/reviewers.toml` names. Any other agent, including your own review-posting agent, is left alone.
- It needs the `agent_type` field in the hook input, which names the subagent (`review-routing:change-reviewer`; a bare `change-reviewer` is recognised too). A Claude Code version that does not send it makes the guard do nothing.
- Claude Code's built-in agents (`general-purpose`, `Explore`, `Plan`, ...) are never guarded, even when your config names one as a reviewer: the same agent type also builds and commits in that session.
- It finds Python the same way as the skills (`scripts/python.sh`) and does nothing without it. The interpreter probe adds one Python start to each call.
- The only way to switch it off is to disable the plugin.

## What it writes

Only when you or Claude run the matching skill: one file per missed bug in the escapes folder, `.claude/mash-workbench/escapes/` by default, and the settings files next to it in `.claude/mash-workbench/` (`add-reviewer`, `record-escape` and `review-changes`; only after you chose where escapes live), `reviews.log` there (`review-changes`: one line per reviewed range that passed, never committed; `record-escape` reads it), `.claude/reviewers.toml` and `.claude/agents/<name>.md` (`add-reviewer`, new reviewers), fix commits for what a review finds (`review-changes`; it never pushes, opens a PR or merges), a line in `CLAUDE.md` naming your check commands when you accept it (`review-changes`), and edits to `CLAUDE.md` or memory files that you approve (`inspect`).

## Upgrading from 0.1.0

`review-pr` is now `review-changes` and no longer opens, comments on or merges pull requests, so nothing needs `gh`. Text in your `CLAUDE.md` or memory that names `review-pr` (add-reviewer used to suggest such a rule) should name `review-changes`; `/review-routing:inspect` finds and proposes those rewrites. The routing script's `--pr` option is gone: pass a range.

## Where escapes live

An escape is a bug in code that a review passed. Each one is a file, `<date>-<slug>.md`, that describes the bug, so `add-reviewer` builds a checklist without asking a git host. The files live in one folder that every worktree of the repository finds: the settings are read from the main worktree (the folder where you cloned the repository), in `.claude/mash-workbench/settings` (for the team; commit it) and `settings.local` (only you; git ignores it through `info/exclude`). The first time a bug needs recording, the skill asks where to keep escapes: `.claude/mash-workbench/escapes` committed (the default, so the whole team's misses add up), the same folder excluded, another folder, or none. New escape files appear as uncommitted changes in the main worktree; no skill commits them.

Who can choose the folder. `REVIEW_ROUTING_ESCAPES` in the environment wins over both files, then `settings.local`, then the committed `settings`. A folder inside the repository can come from any of the three. A folder outside the repository is accepted only from `settings.local` or the environment variable, which are yours: when the committed `settings` file names one, the scripts stop (exit 6) and the session asks you. `settings.local` counts as yours only when git answers that the main repository's index does not track it, and the line `.claude/mash-workbench/settings.local` is in the repository's `info/exclude` (`mash-settings.sh set ... --local` writes it; a commit, a patch or a clone cannot): a repository can commit one, or a patch applied with `git apply` can create one, and the scripts then read it as a committed file. The line stays when you delete the file, so after your first `set --local` a file that a patch creates counts as yours. The scripts name the git directory and the work folder in that question, so git looks for no repository inside `.claude`; a git error counts as tracked. A submodule or a nested repository at `.claude` or `.claude/mash-workbench` is refused (exit 6). Git starts only in a repository that a real `.git` entry names: a folder shaped like a git directory (it holds `HEAD` and `objects/` or `refs/`, which a commit can hold) is refused with exit 6 before any git runs, because git would read its committed config, and that config can name a program to run. This also refuses a bare repository's own folder; its linked worktrees work as before. `.claude` and `.claude/mash-workbench` must be real folders: a symbolic link there is refused, also one that stays inside the repository. A settings file that is a symbolic link is refused, and so is a path with a backslash. The scripts also refuse a linked worktree, a temporary folder, the git directory, a folder whose `README.md` names another repository, and a symbolic link that would move a write or a read: `.claude` and `.claude/mash-workbench`, a link that leads from a path inside the repository to a place outside it, a linked `README.md` or `reviews.log`, and an old ledger file that is a link or sits behind one. A drive-letter path keeps its spelling (`C:/Users/me/escapes`). The environment variable has your trust: the `env` block of a committed `.claude/settings.json` can set it, but Claude Code applies that file only after you accept its workspace-trust dialog.

Setup also offers to add allow rules for two scripts, `escape-add.sh` and `review-log.sh`, to `.claude/settings.local.json` in the main worktree, so background sessions in new worktrees record without a prompt; it adds them only on your yes (the rules and their limits are under "Audit this plugin"). With the sandbox on, a session in a linked worktree also needs `sandbox.enabled`, `sandbox.autoAllowBashIfSandboxed` and `sandbox.filesystem.allowWrite` naming the escapes folder (in a container also `enableWeakerNestedSandbox`). A repository file cannot set `autoAllowBashIfSandboxed`, so the plugin does not try: set them in your own settings.

A ledger in the old one-line format (`docs/mash/review-escapes.md` or `docs/review-escapes.md`) is still counted, but nothing new is recorded until you migrate it: the skill explains and asks, then runs `escape-migrate.sh`, which writes one file per line and leaves the old file for you to remove.

## Audit this plugin

You can read every script before you run it. This section says what each one reads and writes, so you know what to look for. The decisions behind it are in `docs/decisions/0005` and `0006` of the marketplace repository.

Network. None of the scripts is written to make a network call. `tests/test_no_network.sh` in the marketplace repository is a tripwire for that, not proof. It scans every file under `plugins/` that git tracks or would track, except `README.md`, `CHANGELOG.md` and `LICENSE`, and fails when one contains a word from a fixed list: network tools and libraries (for example `curl`, `wget`, `urllib`, `socket`, `ssh`, `rsync`), tools that download code (`npx`, `uvx`, `pip install`), any `gh` command, and `git` with a subcommand that talks to a remote (`push`, `fetch`, `pull`, `clone`, `ls-remote`), also with options or variables before the subcommand and in the quoted list form Python uses. It also fails on a file that is not text, such as a compiled `.pyc`. The matches it accepts are listed in `tests/no_network_allowed.txt`, each with its file, line and reason: comments and regular expressions about remote URLs in `mash-settings.sh` and `escape-add.sh`, the text and tables of `reviewer-guard.py` (it reads a reviewer's command and runs none of them), the hook's description in `hooks/hooks.json`, and prose in the skills. A script can reach a network in a way that is not on the list, so read the scripts too. The reviewer agents run Bash commands that the model chooses, and the plugin does not restrict their network use: the hook allows `git fetch`, `git clone` and `gh` commands that only read.

Writes. `tests/test_write_scope.sh` runs the scripts that write, the router, the hook and most of the scripts that only read (not `find-checks.sh`) from a private copy of the plugin against throwaway repositories. Before and after each run it lists four folders: the folder that holds the repositories, a fresh home folder, a private `$TMPDIR`, and the plugin copy. It fails when a path changed that is not in the table below, and when a script that should only read changed anything. It does not watch any other folder, so a write to a fixed path elsewhere (under `/var/tmp`, or in your real home folder) would pass: it catches the common mistakes and is not proof either. The cases where a script must refuse to write are in `tests/test_escapes.sh`, `tests/test_mash_settings.sh` and `tests/test_review_log.sh`.

The escapes folder is `.claude/mash-workbench/escapes/` unless a setting names another one ("Where escapes live" says who can choose, and what is refused). When you chose a folder outside the repository, that is where `escape-add.sh` writes. The home folder `.claude/mash-workbench/` and `info/exclude` always belong to the main worktree, whichever worktree runs the script.

`MASH_PYTHON` is a command, and the hook runs it on every Bash call. Set it only in your own environment or settings. The `env` block of a committed `.claude/settings.json` can set it too, once you accepted the workspace-trust dialog for that repository; that file can then add hooks of its own as well.

What the hook does. `reviewer-guard` runs on every Bash call in every project, with no prompt, once the plugin is enabled. It acts only for this plugin's reviewers: its own agents and the ones your `.claude/reviewers.toml` names. It refuses a `git` command that changes a real checkout (anything except reads such as `show`, `diff`, `log`, `status`) and a `gh` command that writes to GitHub or changes gh's setup. It reads the command text and never writes a file (`tests/test_write_scope.sh` runs it too). It is a guard against accidents, not a security boundary, and the hook's docstring lists its gaps; a read command with a `git` option that writes a file or runs a program (`--output=`, `-c`, `--ext-diff`) is one of them. A reviewer agent file in your repository can also give itself more tools: the router checks only its model.

The permission prompt. Claude Code asks you before it runs a Bash command, with these exceptions: a command an allow rule covers, a command Claude Code counts as read-only, a sandboxed command when `autoAllowBashIfSandboxed` is on, and every command in auto or bypass mode. Hooks, such as `reviewer-guard`, run without a prompt. A `claude -p` session has nobody to ask, so a command that needs approval is refused there. Where the prompt appears, it is your main control: you can read the script before you say yes.

The optional allow rules. When setup asks where escapes live, it also offers allow rules for two scripts only, `escape-add.sh` and `review-log.sh`. `permission-rules.sh` prints them. The script prints one rule for each spelling of the path that a skill writes, five today: `escape-add.sh` as `add-reviewer/`, as `review-changes/../add-reviewer/` and as `record-escape/../add-reviewer/`, and `review-log.sh` in its two spellings. Each rule names the exact installed path and has one wildcard, at the end, for the arguments (for example `Bash(bash <installed path>/escape-add.sh *)`). Setup adds them to `permissions.allow` in `<main worktree>/.claude/settings.local.json`, and only when you say yes. Claude Code applies that file with no trust step because it is normally untracked; nothing checks that. If your project commits `.claude/settings.local.json`, do not accept the rules: they hold absolute paths of your machine, and they would reach everyone who clones the repository.

After a plugin update. The rules name the plugin's version folder, so they do not match the new version's scripts: a new version needs your yes again. But Claude Code keeps the old version's folder in its plugin cache (`~/.claude/plugins/cache/<marketplace>/review-routing/<version>/`), and the old rules still match the old scripts there. So after each update, run setup step 3 again (the `review-changes` reference describes it): `permission-rules.sh` lists the old rules as `remove:` lines and offers no new rule until they are gone. It reads only the main worktree's `.claude/settings.local.json` and the current linked worktree's; remove the same rules by hand from any other settings file you copied them to. From 0.6.0 on there is a second guard: `escape-add.sh` and `review-log.sh` ask `scripts/plugin-current.sh` first, and a copy in the plugin cache that `installed_plugins.json` no longer lists, for you or for the project of the current folder, stops with exit 6 and writes nothing. It reads the project of a session from the current folder: the folder itself, the top of its git checkout, and the main worktree. The scripts of 0.5.1 and earlier do not have that guard, so for them removing the rules is the only protection. Until the new rules are in, a background session with no user reports its escapes in its answer instead of recording them.

If you accepted the rules that versions 0.4.0 to 0.5.0 offered, remove them. They begin with `Bash(bash */review-routing/`, and the wildcard in them allowed any command that mentions a script's name. The 0.5.1 entry in `CHANGELOG.md` explains the fix, and `permission-rules.sh` lists them as `remove:` lines.

No rules are offered when the plugin folder is inside the repository, for example when you start Claude Code with `--plugin-dir` on a folder of the project: a session that can edit files there could change the scripts and then run them with no prompt. None are offered either when the plugin path holds a character that a rule cannot spell safely (anything but letters, digits, space and `_ . / : @ % + = , ~ -`). The script reads which list a rule is in: `present:` and `remove:` lines are about `allow` lists only, and a note names a current rule that a `deny` or `ask` list also holds.

What the rules still pre-approve, and the other limits:

- Any arguments to `escape-add.sh` and `review-log.sh` at that one path. The scripts open no file that an argument names: `--body` takes the text itself and reads no standard input, and `--body-file` is gone since 0.6.0, because it copied any file the session could read into the escapes folder. `--batch -` reads standard input. Claude Code asks before a redirect from a file outside the session's folders and before a pipe from another command, but not before a redirect from a file inside those folders: such a file becomes escape files only when it already has the block format (frontmatter with `area:`, `class:` and `slug:`); any other file is refused and none of its text is written.
- `<repo-root>` is an argument, but `escape-add.sh` and `review-log.sh add` refuse one that is not in the repository of the session's current folder (exit 6), and Claude Code blocks a `cd` out of the session's folders. A session started in a folder above its repository therefore cannot record.
- No rule is offered on Windows (Git Bash, MSYS, Cygwin): the checks are not tested there, so each run asks you. CI tests Linux and macOS.
- A rule allows a path, not content. Anyone, or any program, that can write to the installed plugin folder changes what runs with no prompt. `permission-rules.sh` looks only at the worktrees of the repository.
- The rule matching was tested on Claude Code 2.1.330 only. A later version can compare rules differently.
- `plugin-current.sh` knows the cache layout of that version. With another layout, an empty registry or one cut in the middle of a write, it cannot tell: it says so in one line on stderr and lets the copy run.

If one of these matters to you, do not accept the rules and approve each call.

Python. The router (`reviewers-for-change.py`) and `reviewer-guard` need Python 3.11 or newer. Without it, `review-changes` uses the prose fallback (only the general reviewer runs, and the review says routing was skipped) and `reviewer-guard` does nothing, so reviewers have no guard. Recording an escape needs only `bash`.

Sandbox users. The Claude Code sandbox is off by default. When it is on, a script can write only inside the session's folder, any folder added with `--add-dir` or `permissions.additionalDirectories`, and the per-user `$TMPDIR`, unless `sandbox.filesystem.allowWrite` names another folder; a session in a linked worktree writes into that worktree. So recording an escape in the main worktree's `.claude/mash-workbench/` needs `sandbox.filesystem.allowWrite` naming that folder; on Linux and WSL2 the folder must exist first, because the documentation says an entry for a path that does not exist yet has no effect. Two more settings are involved: `sandbox.enabled` turns the sandbox on, and `sandbox.autoAllowBashIfSandboxed` removes the prompt for commands that run inside it (it does not grant the write). Inside a container you also need `enableWeakerNestedSandbox`. A file in the repository cannot set `autoAllowBashIfSandboxed`, so the plugin does not try; set these in your own settings. See https://code.claude.com/docs/en/sandboxing.

A prompt you can paste into your own agent. The installed copy is in `~/.claude/plugins/cache/mash-workbench-marketplace/review-routing/<version>/`; in a clone of the marketplace it is `plugins/review-routing`.

```
Review the Claude Code plugin in <folder> for network access, writes outside the repository, command injection and unsafe file handling. Cover the scripts, the hook in hooks/, what each skill (SKILL.md, reference.md) tells the model to run or edit, and what the reviewer agents in agents/ may run. List every finding with file and line. Say which writes go outside the repository, and to which paths.
```

## Pin a version

An update changes the scripts that run on your machine, so you may want to stay on a commit you have read. This section follows the Claude Code documentation at https://code.claude.com/docs/en/plugins/marketplace-reference.md. The `owner/repo@<sha>` form was run once, on Claude Code 2.1.330: `claude plugin marketplace add svelasquezr/mash-workbench-marketplace@<full 40-character SHA>` cloned that commit, `/plugin marketplace list` showed the SHA, and the installed plugin recorded it as `gitCommitSha` in `installed_plugins.json`. The rest was not run.

The documented pin for you, as a user, is the marketplace `ref`: add this marketplace at a commit by giving that commit's full SHA as the `ref` (the form `owner/repo@ref`, or the `ref` field of an `extraKnownMarketplaces` entry). This needs Claude Code 2.1.324 or later. The `ref` and `sha` fields of a plugin source are set by the marketplace author, and the entries in this marketplace are relative paths, so you do not set them.

The documentation names no `plugin install name@version` form: in `review-routing@mash-workbench-marketplace`, the part after `@` is the marketplace, not a version. To check what is installed, run `/plugin marketplace list` and `/plugin`. The documentation does not say whether a marketplace pinned this way still updates by itself, so check after the first update. Each release has a section in `CHANGELOG.md` with the scripts whose behavior changed, so you can see what to re-read before you move to a new commit.

## Why reviewers are routed

One general reviewer misses what a specialist would catch, and a specialist for every path costs more than it saves. Routing by path keeps the cheap general reviewer as the default and adds a specialist only where a miss is expensive or has already happened.

## Uninstall and support

`/plugin uninstall review-routing@mash-workbench-marketplace`. Files the plugin wrote into your repositories stay; delete them if you do not want them. Report a problem or ask a question at https://github.com/svelasquezr/mash-workbench-marketplace/issues.
