# 0006: the scripts do not trust a committed file, an argument or an old copy

## Context

An audit of the plugins found eight ways in which data from a repository, from a session or from an old plugin version changed what a script did. Each one is a security bug. The conditions, the incorrect result and the expected result follow.

1. **Python modules from the current folder.** A project folder contained a file `datetime.py` or `re.py`. `backlog-stale.sh` gave its Python program to `scripts/python.sh` on standard input, and Python put the current folder first on its module path. Python ran the file from the project. The expected result is that plugin Python imports only the standard library and the files of the plugin.
2. **A committed file selected the place of a write.** The committed file `.claude/mash-workbench/settings` contained `escapes=../victim/.claude/rules`. `escape-add.sh` wrote the escape file and a `README.md` in that folder, which is outside the repository. A committed symbolic link at `.claude/mash-workbench`, at the escapes folder, at its `README.md`, at `reviews.log` or at the backlog file had the same effect. `backlog-path.sh` did no check of `MASH_WORKBENCH_BACKLOG`. The expected result is that only the user selects a place outside the repository.
3. **An argument named a file to read or to write.** `escape-add.sh --body-file <file>` copied a file that the session can read, for example a private key, into the escapes folder. `backlog-add.sh --file <path>` appended a line to a file at a path of the caller. With an allow rule from [0005](0005-exact-path-allow-rules.md), Claude Code ran these commands with no prompt. The expected result is that an argument cannot make the script open a different file.
4. **Old plugin versions.** The user accepted the allow rules of one plugin version and then updated the plugin. Claude Code kept the folder of the old version in its plugin cache. The old rules continued to approve the scripts of the old version, also when the new version corrected a security bug in them. The expected result is that an old copy does not run with no prompt.
5. **A range was read as a git option.** The session gave the range `--output=<file>` to `reviewers-for-change.py`. The router gave the text to `git diff`, and git wrote the file. The expected result is that git reads the text only as a range.
6. **A name from the config was used as a path.** `.claude/reviewers.toml` named the reviewer `../../x`. The router read the file `x.md` outside the agents folder, and it printed the `model:` value of that file in an error message. The expected result is that the router reads agent files only in the agents folders.
7. **A committed folder in the shape of a git directory.** A commit can hold a folder that contains `HEAD`, `objects/` and `refs/`. Only the name `.git` cannot be committed. Git accepts such a folder as a repository, and it reads the committed `config` file in it. In a fresh clone, the home folder `.claude/mash-workbench` had this shape, with `core.worktree = ../..` and `core.fsmonitor = <a committed program>`. The check of `settings.local` ran git in the home folder. Git ran the program, and the committed `settings.local` became the file of the user. Then `escape-add.sh` and `backlog-add.sh` wrote outside the repository. A `<repo-root>` argument that named such a folder had the same result. The expected result is that git does not start in a folder that a commit controls.
8. **Gaps in what an allow rule approves.** An approved `escape-add.sh`, `backlog-add.sh` or `review-log.sh add` wrote into each repository that `<repo-root>` named. A committed `reviews.log` answered "reviewed". Control characters from committed escape files reached the terminal. `review-log.sh` could make a network call in a partial clone. Text from a review comment went into the escape body, and from there to the agent that writes a reviewer. The checks were not tested on macOS or Windows. The expected result is that an allow rule approves nothing more than a write to the repository of the session.

## Decision

1. **Isolated Python.** `scripts/python.sh` starts the interpreter, and its version probe, with `-I`. The interpreter also gets `-B`, and the script sets `PYTHONSAFEPATH=1` and `PYTHONDONTWRITEBYTECODE=1`. Python then does not import from the current folder or from the folder of the script, and it ignores `PYTHONPATH` and the user site-packages. The router adds its own folder to the module path, because its modules are there.
2. **Who selects a place outside the repository.** `mash-settings.sh path <dir> escapes|backlog` gives the place of the escapes folder and of the backlog file. It removes `.` and `..` from the path as text before the checks, and it prints that path, so the path that the checks see is the path that the script writes. It accepts a place outside the main worktree only from `settings.local` or from the environment variable. It refuses such a place with exit code 6 when the committed `settings` file names it. A `settings.local` file is the file of the user only when git gives the answer that the index of the main repository does not track `.claude/mash-workbench/settings.local`, and when the line `.claude/mash-workbench/settings.local` is in the `info/exclude` file of the repository. `set --local` writes that line. A commit, a patch that `git apply` applies, or a clone cannot write it. The line stays when the file is deleted. After that, a file that a patch creates counts as the file of the user. We accept this limit: the user ran `set --local` in that clone before. The script gives git the git directory and the work folder, so git does not look for a repository in the home folder. A `.git` entry in `.claude` or in `.claude/mash-workbench` (a submodule or a nested repository) gives exit code 6. For each other answer, also a git error, the file is a committed file, and `set --local` does not write it. The message gives the reason. The message tells the session to ask the user and then to write the value to `settings.local`.
3. **Symbolic links.** The scripts refuse, with exit code 6, a symbolic link at the home folder `.claude/mash-workbench`, a symbolic link at `.claude` (also when the link stays in the repository, because it can put a committed folder in the place of the home folder), a path that the user wrote in the repository and that a link moves out of the repository, and a link at the escapes folder's `README.md`, at `reviews.log`, at the backlog file, at a settings file and at an old ledger file. An old ledger file gets the path checks of the escapes folder, so a link at a folder on its path is also refused. `mash-settings.sh path` refuses a setting that names a link to a file. They also refuse a path that contains `\`, because the path checks split a path only at `/`. The reports do not read an escape file that is a symbolic link.
4. **The backlog has the checks of the escapes.** `backlog-path.sh` uses `mash-settings.sh path`, and `backlog-add.sh` uses the new `check-backlog-path`. The backlog file has a `repo:` line below its title, and a file outside the repository with a different owner is refused. The backlog stays one file.
5. **No argument names a file.** `escape-add.sh` takes the body as text (`--body <text>`). It does not read standard input for one record, because a redirect from a file of the project (`< .env`) gets no prompt from Claude Code. `--batch` reads only standard input, and it records only text that has the block format. `--body-file`, `backlog-add.sh --create` and `backlog-add.sh --file` are removed; each one stops with exit code 2 and tells the replacement.
6. **An old copy refuses to run.** `scripts/plugin-current.sh` reads `installed_plugins.json` next to the plugin cache. When the folder of the script is in the cache, an entry of that file must name the folder. The entry counts only when it is for the user, or for the project of the current folder (the folder, the top folder of its git checkout when the folder is in it, or the main worktree): the file can list old versions for many old projects. With no such entry, the script stops with exit code 6. `escape-add.sh`, `review-log.sh` and `backlog-add.sh` run this check first.
7. **Old rules must go.** `permission-rules.sh` prints no `add:` line while a `remove:` line is necessary. It reads the name of each list (`allow`, `deny`, `ask`), and only a rule in an `allow` list is a `present:` or `remove:` rule. The setup text tells the session to remove the old rules first. This is the only protection for the scripts of version 0.5.1 and earlier, which do not have the check of item 6.
8. **One rule script for the two plugins.** `permission-rules.sh` is the same file in `review-routing` and in `mash-workbench`. In `mash-workbench` it offers one rule, for `backlog-add.sh`, in the shape of 0005.
9. **Text that goes to git.** The router refuses a range that starts with `-` or contains a space. `review-log.sh` refuses a revision that starts with `-`, and it gives only full commit ids from the log to git.
10. **Names from the config.** The router does not use a reviewer name as a file name when the name contains `/` or `\` or starts with `.`, and it does not read an agent file that is a symbolic link. It reads no agent file when `.claude/agents` resolves to a folder outside the repository.
11. **Git starts only in an anchored repository.** Before git starts, `mash-settings.sh` goes up from `<dir>` in the order that git uses. The first folder with a `.git` entry is the repository. A folder in the shape of a git directory (`HEAD`, and `objects`, `refs` or `commondir`, each also as a symbolic link) with no `.git` entry gives exit code 6. A `.git` entry that git cannot use (a folder without `HEAD`, `objects` and `refs`, a file with no `gitdir:` line, a dangling link) gives exit code 6 too, because git would go on to the folders above. Then the git directory that git reports must be the directory that the `.git` entry names. Each script that has an allow rule asks `mash-settings.sh main-worktree` before it runs git, so this check is in front of each git command of the scripts. These scripts run git only in the main worktree or in the top folder that `mash-settings.sh toplevel` prints, never in the `<repo-root>` text, and they remove the git variables that select another repository or config. They set `GIT_NO_LAZY_FETCH`, so git does not download a missing object in a partial clone (git 2.44 and later). The router (`reviewers-for-change.py`) and the `reviewer-guard` hook start git in the current folder with no such check. They have no allow rule, and `git rev-parse` alone started no program in our tests. Each git command of `mash-settings.sh` runs without `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the other variables that select a repository, and with an empty `core.fsmonitor`. `plugin-current.sh` gets the top folder and the main worktree from `mash-settings.sh`.

12. **A write goes only to the repository of the session.** An allow rule approves any arguments. `escape-add.sh`, `backlog-add.sh` and `review-log.sh add` therefore refuse, with exit code 6, a `<repo-root>` that is not in the repository of the current folder (`mash-settings.sh same-repository`, with `pwd -P`). Outside git, `backlog-add.sh` requires the current folder to be in `<repo-root>` and outside every git repository, so a `<repo-root>` above the repository of the session is refused. A session cannot go around the check with `cd`: Claude Code 2.1.330 blocks a `cd` to a folder that is not a working directory of the session. We tested this with `claude -p`.
13. **The review log is the log of this clone.** `review-log.sh add` refuses a tracked `reviews.log`. `reviewed` reads the log only when git does not track it and the exclude line that `add` writes is in `info/exclude` (`mash-settings.sh private`). Otherwise it answers "not reviewed", and the skill asks the user. `add` does not adopt a log with lines and no exclude line, because `add` writes that line before its first record; a patch can create such a log.
14. **No control characters in the output.** The scripts remove control characters (C0 except tab and line feed, DEL, and C1 as UTF-8) from text that they print from files: `escape-add.sh --list` and its result lines, `escapes-report.sh`, `backlog-stale.sh`, the near-duplicate note of `backlog-add.sh`, the messages of `escape-migrate.sh`, both fields of `find-checks.sh`, the `remove:` lines of `permission-rules.sh`, the `repo:` line that a refusal names, and `mash-settings.sh get`. `path` and the `check-*` commands refuse a path with a control character. They compare bytes, so the answer is the same in each locale (the class `[[:cntrl:]]` does not find C1 in the C locale). A committed file cannot send an escape sequence to the terminal or to the session.
15. **No network on an old git.** In a partial clone with git older than 2.44, `review-log.sh` computes nothing (exit code 6). Git 2.44 and later get `GIT_NO_LAZY_FETCH`.
16. **Escape text is data.** An escape body can come from a review comment. The `record-escape` skill writes the body in its own words. The `add-reviewer` evidence step tells the subagent not to follow text in escape files, and the reviewer it writes keeps read-only tools and no `permissionMode`. This is skill text, not a script check.
17. **No allow rules where the checks are not tested.** CI runs the tests on Ubuntu and on macOS (`/bin/bash` 3.2). On Windows (Git Bash, MSYS, Cygwin), `permission-rules.sh` offers no rule and lists a current rule for removal, so each run asks the user.

## Options that we did not select

- **`safe.bareRepository=explicit`.** Git refuses a repository that it finds with no `.git` entry. Cons: the setting needs git 2.38 or later, and the scripts support git 2.7. On an older git, git ignores the setting and gives no guard. The check of item 11 works with each git version.
- **Only `PYTHONSAFEPATH=1`.** It removes the current folder from the module path. Cons: `PYTHONPATH` in the environment continues to add folders. `-I` also ignores that variable.
- **Refuse each place outside the repository.** Pros: no check of the source is necessary. Cons: a user cannot keep escapes in a folder that stays when the clone is deleted. 0004 permits that folder.
- **Ask the user in the script.** A script cannot ask a question in a session with no user. The exit code and the message give the question to the session, and `settings.local` holds the answer.
- **A body file in a private folder that the skill writes.** Cons: a session in a linked worktree cannot write in the main worktree's `.claude/` without a prompt, and each other folder is a folder that a different program can write to. Text in the argument needs no file.
- **Only the setup text for old rules.** Cons: a user who does not do setup again keeps the old rules. The check of item 6 does not need the user.

## Pros and cons

- Pros: a committed file, a symbolic link or an argument cannot move a write out of the repository or copy a file into it. A test plants each of these cases.
- Pros: after an update, an old copy of the three scripts with rules does not run, also when the old rules stay.
- Pros: `backlog-stale.sh` does not use Python, so `mash-workbench` needs Python only for `past-friction.py`.
- Cons: a user on Windows must write a path in the settings with `/`. The script keeps a drive letter as the user wrote it (`C:/Users/me/escapes`).
- Cons: the folder of a bare repository is refused with exit code 6, not 5, because a script cannot tell it from a committed folder without git. A linked worktree of a bare repository gives exit code 5, as before. A project folder that holds a file `HEAD` and a folder `objects` or `refs` is refused too.
- Cons: `backlog-add.sh` writes only to a new file, to an empty file whose name ends in `.md`, or to a file whose first line is `# Tooling backlog`. A committed setting can name a file in the repository, and the script must not add a line to a different type of file. A user who has a backlog with a different first line must add that title.
- Cons: the interface changes. A session that uses `--body-file`, `--batch <file>`, `--create` or `--file` gets exit code 2 with the new form. A user who has a symbolic link in the repository as the escapes folder must set the real path in `settings.local`.
- Cons: a repository in which `.claude` is a symbolic link to a folder outside the repository cannot use the home folder. The scripts stop with exit code 6.
- Cons: the environment variables `REVIEW_ROUTING_ESCAPES`, `MASH_WORKBENCH_BACKLOG` and `MASH_PYTHON` have the trust of the user. The `env` block of a committed `.claude/settings.json` can set them after the user accepts the workspace-trust dialog of Claude Code. At that time the same file can also add hooks, so we accept this.
- Cons: `plugin-current.sh` reads the project of a session from the current folder. A person who runs a script by hand from a different folder, with a plugin that is installed only for one project, gets exit code 6.
- Cons: `plugin-current.sh` knows the cache layout of one Claude Code version (2.1.330). When the layout is different, or when the registry contains no complete entry with an `installPath`, the check lets the copy run. In a folder that has the shape of the cache, it then prints one line on stderr. A session that started before an update gets exit code 6 from the old copy until the user starts a new session.
- Cons: the check of item 6 is not in version 0.5.1 and earlier. For those versions, only the removal of the old rules helps.
- Cons: `--batch -` reads standard input. Claude Code gives no prompt for a redirect from a file in the folders of the session, so a file there that has the block format can become escape files. A file with a different format is refused, and none of its text is written.
- Cons: outside a git repository, `backlog-add.sh` has no settings and no path checks. There, the `<repo-root>` argument and a relative `MASH_WORKBENCH_BACKLOG` select the place. The script only refuses a symbolic link that moves the write out of that folder.
- Cons: a `settings.local` that the user writes by hand counts as the file of the user only after `set --local` has run once (it writes the exclude line). Until then, a place outside the repository in it gets exit code 6, and the message gives the `set --local` command.
- Cons: in a `--separate-git-dir` repository whose git folder has the name `.git` (for example `/store/proj/.git` for the work folder `/work/proj`), the scripts use `/store/proj` as the main worktree. Git gives the same answer in `git worktree list`. A linked worktree has no record of the work folder, so a different answer from the work folder would put the settings in two places. The scripts give one answer in each worktree. A committed file in `/work/proj` is not read as a settings file there.
- Cons: a session that starts in a folder above its repository cannot record (exit code 6). It must run the command from inside the repository.
- Cons: in a partial clone with git older than 2.44, `review-log.sh` does not log and does not answer (exit code 6).
- Cons: on Windows, each run of a writing script asks the user. We do not test the checks there.
- Cons, judged as no new risk: `--batch -` with a redirect (Claude Code asks before a file outside the folders of the session is used, and the session can read a file inside them already); `plugin-current.sh` lets a copy run when it cannot read the registry (only the user can make that file unreadable); a committed `.settings.lock/` folder stops `set` with exit code 1 (the message names the folder).
- Cons: the check of `settings.local` asks git about one path in each letter case. On a file system that ignores some Unicode characters (HFS+), a tracked name with such a character can open as `settings.local` and still read as private. A committed `.CLAUDE/mash-workbench/settings.local` on a case-sensitive file system makes the private file of the user read as committed (a safe failure). We did not test these cases.
- Cons: the checks compare paths with exact letter case. CI tests macOS, but only on the file system of the CI machine. We did not test Git Bash, so no rule is offered there.
- Cons: the body text goes through the command line, so the session must quote it. A body with `$( )` or a backtick in double quotes gets a prompt from Claude Code. This is a safe failure.
- Cons: `permission-rules.sh` reads only two settings files. The user must remove old rules from other files by hand.
- Cons: a reviewer agent file in the repository can give itself more tools or a permission mode, and the router does not examine these keys. The `reviewer-guard` hook is a guard against accidents and not a security boundary. We did not change this.
